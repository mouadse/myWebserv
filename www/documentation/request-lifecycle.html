Lifecycle

One connection, a clear state machine.

Each client is represented by a Client object that tracks request parsing, response buffers, streaming state, and CGI execution. The server moves this state forward on each epoll event.

Client state

The Client object holds the current request, the pending response buffer, and optional streaming state for large files. It also stores all CGI pipe information if a CGI process is active. 

Client
  request: HTTPRequest
  response: HttpResponse
  writeBuffer / writeOffset
  streaming: file FD + buffer
  cgiActive: pipes + pid + output

Read path

  1. Server::readClient reads available bytes.
  2. HTTPRequest::addData advances the parser.
  3. When complete, RequestHandler builds a response.
  4. For CGI, the server spawns a script and returns to epoll.

Write path

Responses are serialized with HttpResponse::toBuffer and sent by Server::writeClient. Large files use the streaming path with a fixed buffer, keeping memory predictable.

If the request includes connection: close, the client is closed after the response is sent.

CGI timeouts

CGI output is collected on non-blocking pipes. The server checks timeouts every loop and terminates scripts that exceed 5 seconds.

The lifecycle is driven entirely by epoll readiness, keeping the server non-blocking at all times.
